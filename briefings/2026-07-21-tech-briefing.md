**Update — Bonsai 27B actually shipped (PrismML, Jul 14, Apache-2.0): a Qwen3.6-27B distilled to 1-bit binary + 1.58-bit ternary weights that runs in 3.9 GB (11 tok/s on an iPhone 17 Pro), and the JARVIS-blocking gap the Jun-28 briefing named is still open — the llama.cpp `Q1_0` CPU path has NEON + scalar only, no AVX2.** *What's new since Jun 28:* that briefing covered llama.cpp **PR #21273** (`Q1_0`/`Q1_0_g128` 1-bit CPU quant) "for the new Bonsai 1-bit models," then still awaiting review; what changed is the model landed — **the flagship 1-bit weights are out**, Apache-2.0, with a **1.58-bit ternary** variant (>95% of full-precision vs the 1-bit's >90%), built on **Qwen3.6**, i.e. your already-supported Qwen family (you run Qwen3.5 DeltaNet SSM). *What's unchanged — and why it matters to you:* PR #21273 merged only `Q1_0_g128`, and its own author noted the **NEON paths were AI-generated + hand-tuned, the generic path is a scalar Q4_0 clone, and no AVX2 kernels were included** — so a Bonsai-class 1-bit model is *not* CPU-runnable on your x86-AVX2 deploy without a hand-rolled `qdot`, which is exactly the fused-AVX2-qdot work you already own. The pull for JARVIS is structural, not "go port a 27B": 1-bit/ternary weights collapse the **memory-bandwidth wall** your deploy is bound by (you tempered 8–9 → 5.46 tok/s on ~2.9 GB/token) — a ~2 B ternary model would cut per-token bytes ~10× vs Q4_K. This is the concrete, shipped end of the TurboQuant/RotorQuant lever you deferred in the Phase-4 ADR. Honest scope: extreme-low-bit needs *models trained for it* (not a post-hoc quant of Gemma 4), the format is `Q1_0_g128`-specific, and the only x86 story today is scalar — a future bench-off contender + an AVX2-kernel exercise, not a task.
