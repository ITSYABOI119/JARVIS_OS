**Systems / OS**

- **The best item of the day for your own code is buried in a RAID patch: Eric Biggers' AVX-512 `xor_gen()` v5 (posted Sep 1) spends 7 of its 8 patches consolidating how the kernel checks XCR0 xstate features for AVX/AVX-512 — moving them to a *single boot-time check* instead of "everywhere kernel code wants to check for AVX support."** That is the Phase-4 M0 problem, in mainline, stated in the author's own words: JARVIS rebuilt the seL4 kernel to XSAVE feature-set 7 specifically so it context-switches YMM, and gates AVX2 on an XCR0.avx probe in both PA and PB. Mainline's version of that check had sprawled far enough to *block* an unrelated optimization from merging (it missed 7.3 over `cpu_has_xfeatures()` confusion and its absence on UML). Third consecutive week of "the feature probe cost more than the thing it guarded," after the Zstd BMI2 finding. Results on a 9950X are strong for 4–8-disk arrays; targeting 7.4. [Phoronix](https://www.phoronix.com/news/AVX-512-xor-gen-v5) · [v5 series](https://lore.kernel.org/lkml/20260901145740.42337-1-ebiggers@kernel.org/#t)
- **Amazon Linux 2027 went to public preview (Sep 3) with its x86-64 packages now targeting `x86-64-v3` — i.e. AVX/AVX2 assumed as a hard floor — plus `-O2` + LTO + auto-vectorization everywhere, Linux 7.1, GCC 16.1, SELinux enforcing.** Nothing to act on, but it is a useful calibration for the deployed box: the 2700X (Zen+) *does* satisfy v3, so the hyperscaler baseline has now moved to exactly the ISA level JARVIS's hand-written `qdot`/attention kernels already assume, and no further. The next baseline step (v4 = AVX-512) is the one that would leave this silicon behind. [Phoronix](https://www.phoronix.com/news/Amazon-Linux-2027-Preview) · [AWS announcement](https://aws.amazon.com/about-aws/whats-new/2026/09/announcing-amazon-linux-2027/)
- **Linux 7.3 now disables RandStruct by default whenever Rust support is present (merged ahead of 7.3-rc2, Sep 3).** RandStruct randomizes kernel struct layout at build time and does not support Rust, so its Kconfig dependency was keeping Rust out of `allmodconfig` — the fix was to drop the hardening default rather than the coverage build. Worth noting as a defaults-erosion pattern more than a threat: a security feature turned off *by default* to unblock tooling is the shape of change that stops appearing in anyone's threat model. Your own analogue is the opposite habit — `build_jarvis_x86.sh` re-asserts its 10 kernel-config invariants every build precisely because a silently-changed default (the persisted `KernelIOMMU=OFF` cache value, A10) is invisible otherwise. [Phoronix](https://www.phoronix.com/news/Linux-7.3-RandStruct-Rust) · [v4 patch](http://www.mail-archive.com/linux-kernel@vger.kernel.org/msg2653344.html)
- **Update (ACE, last touched Jul 9 when Intel *posted* the first patches): the initial ACEv1 enablement is now MERGED into GCC 17 (Sep 2), with a concrete flag — `-macev1`, which implies AVX10.1 + AVX/AVX2 + SSE/SSE4.** GCC 17.1 lands ~Mar–Apr 2027; LLVM enablement is in flight ([PR #208408](https://github.com/llvm/llvm-project/pull/208408)). Unchanged conclusion, firmer date: the cross-vendor successor to AMX is now a real compiler target rather than a proposal, and neither it nor AMX exists on the 2700X — so this remains a "which ISA to aim the next matmul kernel at" marker for a future box, not a lever. The `-macev1` implication set is the useful new detail: ACE arrives *on top of* AVX10.1, so the AVX2 kernels you have are not the migration path to it. [Phoronix](https://www.phoronix.com/news/GCC-17-Merges-ACE-v1)
