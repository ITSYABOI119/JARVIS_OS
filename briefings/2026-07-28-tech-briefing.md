# JARVIS Daily Tech Briefing — Tuesday, July 28, 2026

**Lead — Update: the seL4 16.0.0 breaking-change list is now extractable, and several items land directly on JARVIS's x86 SMP + respawn code (Jul 27 gave the headline but couldn't pull the specifics).** The docsite release notes read cleanly this run. The three that touch your actual code: **(1) `seL4_TCB_ReadRegisters`/`WriteRegisters` now respect `count`** — "previously [they] ignored the count parameter and unconditionally copied the entire `seL4_UserContext`." Your K/M2a-2 reuse-in-place respawn is exactly `ReadRegisters → mutate → WriteRegisters` (preserving `fs_base`); on 16.0.0 a partial `count` would no longer copy the whole context, so that path must be re-checked before any upgrade. **(2) x86: "Fix PC corruption when exiting kernel lock via `ipiStallCoreCallback()`"** — a race where a thread entering the kernel lock while its core is being stalled gets its restart PC corrupted. That's your exact multicore config (`NUM_NODES=6`, equal-prio round-robin, IPI core-stalls) — a real SMP correctness fix. **(3) x86 ACPI hardening:** "validation for BIOS-provided MADT entry size + aligned access" and an "interrupt source override padding" fix — your SMP/APIC bring-up parses MADT. Also: **`seL4_UserTop` is deprecated** in favor of a new inclusive `seL4_UserVSpaceTop`, and a new **`seL4_DebugGetThreadAffinity()`** complements the `seL4_TCB_SetAffinity` you use for worker pinning. **Security substance:** 16.0.0 fixes a **Critical x86-64 VM escape in `restore_vmx()`** (affects 13/14/15.0.0, unverified x86-64 **with VT-x + `KernelX86_64VTX64BitGuests`**) — **JARVIS is not exposed**: you pin a 15.0.0-era kernel (`d22affe8`) but run no VT-x/VCPU/guest (you're a rootserver running inference, not a hypervisor). Nothing forces the bump; it's an evaluate-and-migrate call, but now you can see what you'd be diffing.
