# JARVIS Daily Tech Briefing — Monday, July 13, 2026

**Quiet day on the wire — so today's lead is a code finding, not a news item.** Nothing net-new landed on seL4, the CPU/SIMD inference path, quantization, or edge-model releases in the Jul 12–13 window. What I did surface is a never-briefed llama.cpp **GGUF-parser security advisory** — and, checking it against your tree, **one of its six findings is an open gap in your own `gguf_parser.c` today.**

**Lead — the llama.cpp GGUF parser advisory (oss-security, May 15, 2026; never briefed) lists six parser bugs, and V-01 is live in JARVIS's parser: `general.alignment` is read from the file with no validation.** The advisory's V-01 (rated CRITICAL) is that upstream bounds `general.alignment` for power-of-2 and non-zero but has **no upper bound**, so a crafted value overflows `GGML_PAD` → arbitrary file seek / OOB read. **Your `gguf_parser.c` is weaker than the code they're calling vulnerable**: `phase3/src/ai/gguf_parser.c:356-366` takes the KV value verbatim (`ctx->alignment = ctx->kv[i].value.u32;` — no power-of-2 check, no zero check, no cap), and line 388 feeds it straight into a mask-based align-up:

```c
uint64_t align = ctx->alignment;
ctx->data_offset = ((uint64_t)pos + align - 1) & ~(align - 1);
```

`align = 0` → `~(0-1)` = 0 → `data_offset = 0`; a non-power-of-2 → a garbage mask; a huge value → the data block lands nowhere near the file. Every subsequent tensor read is keyed off that offset. *Why it matters:* same class as, and same threat model as, the `gguf_vocab` overflow-safe-subtraction fix you shipped Jun 30 — the GGUF is owner-provisioned (semi-trusted), so this is defense-in-depth, not a live exploit path. Fix is three lines (reject `align == 0`, non-power-of-2, and `> 1 MiB` — the advisory's own recommended bound). *The good news, verified:* the other five are **already covered** in your tree — V-03 (`n_dims > GGUF_MAX_DIMS` rejected, `:288`), V-05 (KV type `switch` has a `default → GGUF_ERR_FORMAT`, `:269`), V-06 (`block_sz == 0 || type_sz == 0` guard in `ggml_tensor_bytes`, `:187`), V-04 (SEC-003 overflow checks on the dim product, `:296`), V-02 (fixed-size buffers + the 1 MB cap in `gguf_vocab`, vs upstream's 1 GB `GGUF_MAX_STRING_LENGTH`). Your hand-rolled parser beats the reference on 5 of 6 — worth closing the sixth. ## Systems / OS

- **GhostLock (CVE-2026-43499) — a 15-year-old use-after-free in Linux's futex priority-inheritance code gives any local user root, and escapes containers (disclosed Jul 8, never briefed).** In-tree since 2011, ships by default in essentially every distro, 97%-reliable public exploit, ~5 s to root; fixed in April (`3bfdc63936dd`), but the *first* fix introduced a crash bug (CVE-2026-53166) whose cleanup was still settling upstream in early July — so "patched" builds may not be. *Why it matters:* it's the TCB argument in one CVE — a routine threading syscall reachable by any unprivileged process crosses straight into Ring 0, because in a monolithic kernel that code *is* the kernel. JARVIS's whole bet is that this class of surface sits outside the trusted core. The other half is the trend: GhostLock was found by an **automated bug-hunter** (Nebula's VEGA), days after Bad Epoll (CVE-2026-46242) in adjacent code — old, heavily-used machinery nobody had reread in years, now being combed by tools. Your hand-rolled parsers are exactly that kind of code.
