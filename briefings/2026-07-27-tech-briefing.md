**Lead — seL4 16.0.0 (22 Jul 2026): the first kernel major-version bump since 15.0.0 (31 Mar), carrying breaking changes on x86_64 and for direct seL4-API users — squarely on JARVIS's path.** *Correcting the record:* the Jul 26 briefing asserted "there is NO seL4 16.0.0" and blamed a search-summary confabulation, on the basis that GitHub's release list still showed 15.0.0 as Latest. **That was the error** — GitHub's "Latest" badge and the search mirrors are stale (they still return 2.1.0/1.4.1 for Microkit); the Foundation's canonical news page ([sel4.net/news](https://sel4.net/news/2026.html)), fetched directly this run, plainly announces the release dated **22 Jul**, with docsite release links, and the release-note wording is echoed independently in search. *What shipped:* seL4 **16.0.0**, Microkit **2.3.0**, CAmkES **3.13.0**, capDL **0.6.0**, rust-sel4 **5.0.0**. *Why it matters to you, concretely:* the announcement states seL4 16.0.0 "and the corresponding Rust support have breaking changes and will require updates if you are using the seL4 API directly" — JARVIS's x86 rootserver (`main_x86.c`: `seL4_Untyped_Retype`, `seL4_TCB_SetAffinity`, the ReadRegisters/WriteRegisters respawn path) is exactly that — and "the Microkit release … has breaking changes for x86_64 systems." CAmkES/capDL only add domain-schedule units (backwards-compatible). *Honest scope:* you pin a specific kernel (`d22affe8`) and already run KernelFastpath + SMP + XSAVE **outside** seL4's verified X64 config, so nothing forces an upgrade — but a major-version bump with breaking API changes on x86_64 is a deliberate evaluate-and-migrate decision, not a drop-in, and it's the first one this project has faced. The specific breaking-change list is in the 16.0.0 / Microkit 2.3.0 docsite release notes (linked from the announcement; those detail pages weren't extractable this run — read them before you diff).
