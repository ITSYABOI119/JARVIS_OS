# JARVIS Daily Tech Briefing — Thursday, July 2, 2026

**Lead — Linux 7.3's first headline change is a "simple DIO" fast-path that kills the software overhead on small NVMe reads (merged to `vfs-7.3.iomap`, Jul 1).** Bytedance's Fengnan Chang traced a "significant bottleneck" in 4K random reads on Gen5 NVMe to the kernel's **iomap direct-I/O path** — the CPU was burning cycles on per-I/O memory allocation and the iomap state machine, not the device. The fix adds a stripped-down DIO path taken when the request is ≤ the inode blocksize (unencrypted inode, etc.), lifting 4K randread **1.92M → 2.19M IOPS** and up to **+10% on EXT4/XFS** with io_uring at high queue depth. *Why it matters:* JARVIS's storage is a hand-rolled **polled NVMe + FAT32** stack. The GGUF stream is large-sequential, but your **Phase-5 memory paths are exactly this small-I/O case** — `epi_store_read` fetches single 512-byte episodic records, the G3/M5 post-reboot recall does *one* bounded 512-byte record read per hit, and `nvme_log` writes 512-byte entries. Mainline's finding — that for sub-blocksize I/O the *bookkeeping* dominates, not the SSD — is a direct design lesson: keep the per-record read path allocation-free and branch-lean (you already bounce single records through a fixed buffer; this validates that instinct). Same engineer/subsystem as the Jun-24-briefed iomap `memset` removal, but a distinct, net-new change. ## Systems / OS

- **Microsoft shipped the first public preview of Linux Containers on WSL ("WSLC", in WSL 2.9.3) — Jun 29.** Native `wslc` container lifecycle, day-one GPU support, and a switch to **VirtIOFS as the default FS for up to ~2× faster** container file I/O. *Why it matters (workflow, not runtime):* your whole seL4 build flow runs in WSL (`build_and_copy_kernel.sh`, the Phase-1/2 test scripts); a containerized WSL target is a cleaner way to pin the aarch64/x86-64 cross-toolchain than a mutable WSL rootfs — reproducible builds without a full VM. Adjacent to your dev box, not JARVIS's stack.
