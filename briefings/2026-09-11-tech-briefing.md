# JARVIS Daily Tech Briefing — Friday, September 11, 2026

**Lead — today's theme is redundant copies nobody noticed, and the sharpest statement of it is DejaVu (arXiv:2609.05635, never briefed).** Its premise: on unified-memory hardware, applications still allocate a CPU buffer *and* a GPU buffer and `memcpy` between them — burning bandwidth, time and energy to move data across a boundary that does not physically exist — purely because the abstraction was inherited from portable discrete-GPU code. **The part worth reading is the caveat, not the speedup:** the authors explicitly refuse to just merge the two buffers, because a program may depend on the buffers being *distinct*, or on the copy itself *ordering* CPU and GPU accesses. So DejaVu-SR is an LLVM pass that **proves** safety before rewriting, and DejaVu-DR is a profile-guided binary rewriter that preserves the ordering effect of each copy it removes. Measured on seven benchmarks across three Jetsons: up to **6.9×** on copy-dominated workloads, 1.10–1.14× end-to-end on closed-source apps, ≥99% of hand-optimised performance. **Why it lands here:** JARVIS already took the zero-copy side of this trade — `resolve_qtensor` hands out pointers *into* the mapped model region rather than copying tensors out — and yesterday's `gguf_tensor_in_bounds()` hardening (`43c60d1`/`a8f664e`) exists precisely because that choice converts a bad declared offset from a bad memcpy into a live OOB pointer. DejaVu is the other half of the same ledger: it names, with a proof obligation attached, exactly what you must establish before deleting a copy — aliasing *and* ordering — which is the checklist to reuse the next time a copy on the PA↔PB path looks removable. [arXiv:2609.05635](https://arxiv.org/abs/2609.05635)

**seL4 / Microkernels**

- **Violet: full virtualization for M-mode RTOS on RISC-V (arXiv:2609.09833, submitted Sep 9).** RISC-V's H-extension virtualizes only U-mode and S-mode — **M-mode, where FreeRTOS and Zephyr actually live, is excluded**, so an unmodified RTOS cannot run in a VM. Violet combines the hardware virtualization features with software emulation of M-mode, runs unmodified RTOSs alongside Linux on SiFive HiFive Premier P550 hardware, and — the honest part — **quantifies the overhead it introduces** on M-mode CSR accesses, timer-interrupt latency and context switching rather than only reporting the win. Relevant as the mixed-criticality problem seL4 attacks from the opposite direction (MCS, functional correctness proved on RISC-V in June, AArch64 port under DARPA PROVERS). [arXiv:2609.09833](https://arxiv.org/abs/2609.09833)

**Local LLM Inference**

- **llama.cpp `b10875` (Sep 9) formally deprecates `--mmap` / `--mlock` / `--dio`**, completing the July `b10105` consolidation into a single `--load-mode {auto,none,mmap,mlock,mmap+mlock,dio}` enum. **Two footnotes matter more than the deprecation:** mixing old and new flags silently keeps only the last one, and the refactor has an open regression — [#26110](https://github.com/ggml-org/llama.cpp/issues/26110) reports it **removed the only safe combination for `--n-cpu-moe` CPU-offload** ("no mmap, but pin the CPU-resident tensors"). Your Main-PC extractor bake-off is pinned to `b8728`, which predates the whole refactor — the pin is doing real work here, not just reproducibility theatre. [b10875 discussion](https://github.com/ggml-org/llama.cpp/discussions/27912)
- **PELM (arXiv:2609.09662, submitted Sep 9, SenSys'26): "not all tokens require full-depth inference."** Adds two *workload* knobs beside the usual DVFS frequency tuning — speculative decoding and **variable verification depth** — for up to 23.1% speedup and 52.4% energy reduction at comparable task quality, code released. Its framing is thermal/mobile, which your 2700X desktop is not; the transferable piece is verification depth as a tunable, and the standing cost is that speculative decoding needs a second resident draft model — a heap re-budget on a box already carrying Gemma 4 E2B plus the 1024-d embedder. [arXiv:2609.09662](https://arxiv.org/abs/2609.09662) · [code](https://github.com/imec-nu/PELM)
- **Tip is `b10896` (Sep 10)** — a DFlash-with-vision fix stopping fixed image offsets from starving the drafter's token allocation; `b10877` (Sep 9) is CUDA MoE MMQ tile sizing on RDNA3. **Scoped claim on the x86 standing pattern: I verified `b10877`, `b10896` and the `b10875` CLI change and none touches an x86 CPU/SIMD kernel — I did not read every build in `b10878..b10895`, so treat this as "nothing found," not "nothing landed."** [b10877](https://github.com/ggml-org/llama.cpp/releases/tag/b10877) · [release history](https://freedom.tech/project/llama-cpp/)

**Systems / OS**

- **Btrfs Zstd decompression: every delivered byte is currently written twice** (queued to `for-next` for Linux 7.4, Sep 9). Usama Arif's fix is to choose the output buffer per streaming call rather than stage-then-copy; ~3% on random 4K reads. Small number, but it is the *lead's* defect class found in a hot kernel path that has been shipping for years — and it follows August's finding that in-kernel Zstd was re-probing CPUID per call. **The convergent lesson your build already follows: probe features once at init, and never stage a byte you can write in place.** [Phoronix](https://www.phoronix.com/news/Btrfs-Zstd-Faster-Decompress)
- **OpenSSL 4.1 Alpha 1 (Sep 9)** — DTLS 1.3, TLS GREASE, more AVX-512 work. Noted and dismissed on the spot for honesty's sake: **Zen+ has no AVX-512**, and your control-IN crypto is a vendored public-domain SHA-256 plus your own constant-time HMAC verify, not OpenSSL — so this is zero-action for the box. [Phoronix](https://www.phoronix.com/news/OpenSSL-4.1-Alpha-1)
