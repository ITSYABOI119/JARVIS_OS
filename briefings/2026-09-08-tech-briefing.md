# JARVIS Daily Tech Briefing — Tuesday, September 8, 2026

**Lead — llama.cpp shipped a Gated-DeltaNet correctness fix (PR #28068, in `b10828`, Sep 6): the q/k L2-norm was using `ggml_l2_norm`, which clamps by `max(norm, eps)` instead of `rsqrt(sum + eps)` — i.e. epsilon *outside* the root, which in the normal case means no epsilon at all where flash-linear-attention has one inside it. And JARVIS's own DeltaNet is already on the correct side of it.** This is the one item today that lands directly on `phase3/src/ai/ssm.c`, the hand-written Gated DeltaNet backing the Qwen3.5 SSM family. **Checked rather than assumed — `ssm.c:43` reads `float inv_norm = 1.0f / sqrtf(sum_sq + eps);`, epsilon inside the root, the form upstream just converged to**, and `deltanet_*` calls it for both `q_norm` and `k_norm` before the `1/sqrt(head_k_dim)` scale (which the source already annotates as verified against llama.cpp's `build_delta_net_autoregressive`). **The reason to read the upstream thread anyway is the pattern, not the patch: three independent reimplementations, two got it wrong the same way.** HuggingFace `transformers` made the identical substitution when it first added Qwen3-Next and corrected it three days later (PR #40842); llama.cpp carried it at *every* GDN call site in the tree until now; vLLM and SGLang vendor the FLA library rather than reimplementing it and never had the bug. **The failure mode is the dangerous one — no crash, no NaN, just a silently different normalization on well-conditioned inputs, which is exactly the class the JARVIS parity gates exist to catch and exactly the class a "looks coherent" smoke test does not.** Worth a look at `test_ssm.c`'s tolerance the next time that path is touched: matching the *old* llama.cpp would now be the failing condition. ⚠️ **One honesty flag on sourcing: the tracker's index card for `b10828` describes the GDN rsqrt fix while the release page for the same build describes `Spark2_5ForCausalLM` architecture support, and the upstream note itself is machine-summarised as unreadable — the `b10818...b10828` diff spans both, but which change is *in* which tag is not established here.** [b10828](https://freedom.tech/posts/2026-09-06-llama-cpp/) · [release history](https://freedom.tech/project/llama-cpp/)

## Quantization

- **"When Quantization Breaks Memory: Recurrent-State Write-Back in Low-Precision Temporal Inference" (arXiv:2609.04490, Sep 3 — never briefed, and it is the same nerve the lead touches).** The claim: in a recurrent network the *rule used to store* the quantized state changes the next step's computation, independent of the arithmetic. Holding a trained GRU fixed and swapping continuous state propagation for deterministic 4-bit state storage raised estimation error **~70× and ~300×** on two parameters, because repeated small updates fell below the write threshold and the stored state froze while the network kept proposing change; error feedback recovered accuracy with no retraining, and the failure reproduced in an independently trained LSTM. **Two honest caveats before anyone reads it as a JARVIS finding: the domain is fluorescence-lifetime imaging, not language, and JARVIS's DeltaNet state `S[]` is plain `float`, not quantized — only the weights are.** It matters as a *design constraint recorded in advance*: if the recurrent state ever gets quantized to save the KV-equivalent footprint, the state-storage interface is the thing to instrument, not the matmul. Their own sharpest result is the counter-intuitive one — **increasing state precision can make a fixed recurrent solution worse**. [abs](https://arxiv.org/abs/2609.04490)

## Systems / OS

- **Zen 6 introduces BTB context isolation, and the patch's own wording is the part that concerns this box (Sep 7).** Borislav Petkov's `tip/x86/bugs` patch says Zen 6's branch-target-buffer protection isolates user/kernel and guest/host contexts, making the SafeRET SRSO mitigation *unnecessary there* — leaving user/user and guest/guest to IBPB-on-context-switch. **Read the complement: SRSO affected Zen 1 through Zen 4, and the JARVIS box is a Ryzen 7 2700X (Zen+), squarely inside that range and running a microkernel with no speculative-execution mitigation infrastructure at all.** Not actionable and not new exposure — the box is a supervised, LAN-local appliance with a single tenant — but it is the honest framing for any future claim about isolation on this hardware: PA↔PB separation is a *capability* boundary, and this class of attack goes underneath it. [Phoronix](https://www.phoronix.com/news/Linux-Preps-AMD-BTB-CTX) · [commit](https://git.kernel.org/pub/scm/linux/kernel/git/tip/tip.git/commit/?id=ae1d2082d93bc04604dc08e9b7f9cdba5e0c28e6)
- **LLVM developers are discussing enabling the ClangIR build by default (Sep 6).** A build-flag flip, not a codegen change, but ClangIR is a new IR layer between the AST and LLVM IR — worth knowing it is coming, given that JARVIS's host-side parity harnesses (the embed vector probe, the GATE 2′ comparator) are the one place clang codegen differences are already the recorded explanation for a ~1e-7 residual.
