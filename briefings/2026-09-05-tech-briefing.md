# JARVIS Daily Tech Briefing — Saturday, September 5, 2026

**Thin day. The one substantive net-new item is a kernel-architecture paper you have not seen: the "fluid kernel" — Federico Terraneo's Miosix design, written up from his Hackaday Europe talk on Sep 3, with a peer-reviewed paper behind it.** The claim is process abstraction *without an MMU*, built on the Memory Protection Unit that 32-bit microcontrollers already carry: applications can be hosted in kernelspace **or** userspace as needed, POSIX-compliant identically on both sides, and the whole thing collapses to a unikernel via a compile-time option that removes process support and shrinks the image. **Why it belongs in a seL4 briefing: the author's own justification list for isolating is, almost verbatim, JARVIS's PA↔PB argument** — "if a process crashes, it does not crash the rest of your embedded system", "you can use privileges to limit damage if a process gets compromised", "you can download and execute new code without rebooting". That is the K/M2 self-heal case (PB faults, PA respawns, box keeps serving) made independently, on hardware two orders of magnitude smaller, by someone who reached it from the RTOS side rather than the verification side. **The honest contrast is the useful part, and it cuts your way:** you get that isolation from real seL4 processes with MMU-backed address spaces and capability-mediated IPC — the fluid kernel is buying a *weaker* version of it (MPU regions, no virtual memory) and paying for it with a compile-time switch that changes whether isolation exists at all. The write-up's own framing of microkernels as "mostly only seen in niche uses where high security and/or safety is critical" is the standing external read of the architecture you build on. **And a commenter asked for precisely the number nobody has: Miosix MPU context-switch overhead vs seL4.** It does not exist; if it ever gets measured it is the direct comparison point for your own IPC path. [Hackaday write-up](https://hackaday.com/2026/09/03/hackaday-europe-2026-fluid-kernels-and-optimizing-c-for-mcus/) · [IEEE paper (no paywall)](https://ieeexplore.ieee.org/abstract/document/11173649) · [Miosix](https://miosix.org)

**Systems / OS**

- **Fedora 47 change proposal filed Sep 4: switch from fat LTO to Thin LTO, with a new RPM macro to make it adoptable per-package.** The stated case is that ThinLTO is faster and far more memory-efficient at link time while keeping most of full LTO's performance, so packages currently using *no* LTO could plausibly turn it on. Still needs a FESCo vote. **The on-path read is a warning, not an invitation: LTO would break the verification method every JARVIS flag flip has depended on.** Your OFF-identity gates compare `main.c.obj` / `llama_quant.o` section-by-section — `.text`, `.rodata`, `.data`, `nm` — precisely because per-object codegen is stable and comparable. Under LTO codegen moves to link time and there are no meaningful per-object sections to diff; you would be left comparing whole images, which this project has already recorded as invalid (DWARF avalanches through the compressed payload — "never md5 a packed image"). If a build-flag change is ever proposed for the box, that gate is the thing it costs. [Phoronix](https://www.phoronix.com/news/Fedora-47-Considers-Thin-LTO) · [F46 predecessor thread](http://www.mail-archive.com/devel@lists.fedoraproject.org/msg215184.html)
