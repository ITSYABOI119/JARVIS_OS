**Lead — llama.cpp fixed an A-matrix indexing bug in its CPU `simd_gemm` scalar tail-column path (b9916, #25390, Jul 8).** The reference engine's SIMD GEMM was indexing the A matrix wrong in the *scalar tail-column* path for full row blocks — the leftover columns a tiled/vectorized matmul cleans up scalar after the SIMD-width blocks. *Why it matters:* you hand-roll your own tiled matmul with exactly this structure (`tensor_ops.c` tiled matmul + unroll, `qmatmul_vec` / `qdot`), and the tail remainder is the classic place an off-by-one hides — coherent-looking output, subtly wrong math. Not your code, but a free "go re-check your own scalar tail path" signal in the single hottest op class you have (matmul) — the same reference-engine-edge-case value as the Jul-6 quantized-`concat` fix. ## Systems / OS

- **Intel posted the first GCC patches for "ACE" (AI Compute Extensions) — the cross-vendor x86 successor to AMX for matrix-multiply/ML (Jul 2, never briefed).** The Intel/AMD x86 Ecosystem Advisory Group firmed up ACE as the successor to Intel's Advanced Matrix Extensions, and Intel engineers have now posted the initial GCC compiler-enablement patches. *Why it matters (direction, not drop-in):* JARVIS's deployed inference is CPU matmul-bound (you tempered the ~8–9 tok/s aspiration to 5.46 as memory-bandwidth-bound), and ACE is where x86 matmul acceleration is consolidating — one cross-vendor tile-matmul ISA both Intel *and* AMD will ship, versus AMX being Intel-only. Doubly out of reach on your current silicon (the Zen+ 2700X has neither AMX nor ACE), so it's a "which ISA to aim the next matmul kernel at" signal for a future box — not something to use now, but the successor worth tracking beyond AVX2.
